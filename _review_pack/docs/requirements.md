# ppi-file-downloader 要件定義書（レビュー版）

## 1. プロジェクト概要

### 1.1 プロジェクト名
ppi-file-downloader

### 1.2 目的
建設情報サービス「ppi.jp」のWebサイトから、ユーザーが指定した条件に基づいてファイルを自動的にダウンロードし、指定したフォルダに整理して保存する自動化ツールを開発する。

### 1.3 対象サイト
- **入口ページ**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Index.htm
- **検索画面（実運用で使用）**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Search/Search/Search.aspx?tab=4
- サイト名: 建設情報サービス

## 2. 機能要件

### 2.1 コア機能

#### 2.1.1 HTML構造解析機能
- **FR-001**: 対象サイトのWebページのHTML構造を解析できること
  - **対象ページ**: 入口ページ（Index.htm）および検索画面（Search/Search/Search.aspx?tab=4）
  - **受け入れ条件**: 検索ページのHTMLを取得し、フォーム要素、ドロップダウン、テーブル構造を正しく解析できること
- **FR-002**: ページ内のファイルリンク（PDF、Excel、Wordなど）を検出できること
  - **受け入れ条件**: 詳細表示（遷移またはポストバック）後のHTMLまたはダウンロード応答から、添付ファイル取得に必要なURL/POSTパラメータを特定し、保存できること
    - 注: 現時点では`dgrKokoku`および`dgrKeika`テーブル、`KokaiBunshoServlet`などのパターンを想定しているが、サイト構造変更時は解析ロジックの調整が必要
  - **対応ファイル種別**: 
    - 拡張子あり: `.pdf`, `.xlsx`, `.docx`, `.xls`, `.doc`, `.jpg`, `.png`
    - 拡張子なし: Content-TypeヘッダーまたはContent-Dispositionヘッダーから判定
    - ZIPファイル: 必要に応じて展開処理を検討（将来拡張）
- **FR-003**: HTMLの階層構造（ページタイトル、発注機関、工事名（文字列検索）、カテゴリ、日付など）を抽出できること
  - **受け入れ条件**: 検索結果ページまたは詳細表示ページから、発注機関名、工事名称、公告日、開札日、契約日などのメタデータを抽出できること
    - 注: メタデータの抽出方法はサイト構造に依存するため、構造変更時は解析ロジックの調整が必要

#### 2.1.2 条件指定機能
- **FR-004**: ユーザーが事前にダウンロード条件を設定できること
  - 対象ページURLの指定
  - ファイルタイプのフィルタリング（拡張子指定）
  - 発注機関や工事名
  - キーワード検索条件
  - 日付範囲の指定
  - その他のカスタム条件
  - **受け入れ条件**: GUI上で検索条件を設定し、設定ファイル（YAML）に保存・読み込みできること

#### 2.1.3 自動ダウンロード機能
- **FR-005**: 指定した条件に一致するファイルを自動的にダウンロードできること
  - **受け入れ条件**: 指定条件で検索し、添付が存在し、かつ取得可能なものは全件保存する。取得不能なもの（サイト側の不具合、認証切れ、アクセス権限なし等）は失敗としてログに残し、実行結果サマリーに件数を出力すること
  - **失敗時の記録項目**:
    - HTTPステータスコード
    - 例外種別（タイムアウト、接続エラー、HTTPエラー等）
    - 対象URL
    - 再試行回数
  - **実行結果サマリー**: 失敗理由別件数を出力すること
    - ネットワークエラー（タイムアウト、接続エラー）
    - 429（Too Many Requests）
    - 5xx（サーバーエラー）
    - 4xx（クライアントエラー）
    - その他
- **FR-006**: ダウンロード進捗状況を表示できること
  - **受け入れ条件**: GUI上で進捗バー、成功/失敗/スキップ件数をリアルタイム表示できること
- **FR-006-1**: ダウンロード処理をユーザーがキャンセルできること
  - **一時ファイルの扱い**:
    - ダウンロード中は常に `.part` 拡張子で保存し、成功時にリネーム
    - キャンセル時は `.part` ファイルを残す/削除する（設定で選択可能）
    - 推奨: `.part` を残す（次回実行時の判定に使用可能）
  - **`.part` ファイルの再開について**:
    - `.part` は次回実行時に「削除」または「上書き再取得」を基本とする
    - HTTP Range による途中再開（レジューム機能）は将来拡張とする
  - **受け入れ条件**: キャンセル操作後、進行中の通信を中断し、安全に処理を終了すること。`.part` ファイルの扱いは設定に従うこと。GUIが固まらないこと
- **FR-007**: ダウンロード失敗時のリトライ機能を有すること
  - **リトライ方針**:
    - リトライ回数: 3回（設定可能）
    - リトライ間隔: 指数バックオフ（1秒、2秒、4秒）
    - 対象エラー: タイムアウト、5xxエラー、429（Too Many Requests）
    - 対象外エラー: 4xx（クライアントエラー、404など）、認証エラー
  - **429エラー時の待機戦略**:
    - `Retry-After`ヘッダーが存在する場合は、その値に従って待機
    - `Retry-After`ヘッダーが存在しない場合は、指数バックオフを使用（最大待機時間: 60秒）
  - **受け入れ条件**: ネットワークエラー時に自動リトライし、3回失敗した場合のみエラーとして記録すること。429エラー時は適切な待機時間を確保すること
- **FR-008**: 既にダウンロード済みのファイルをスキップできること（重複回避）
  - **重複判定方法**（優先順位順）:
    1. **URL同一判定**: 同一URLのファイルは常にスキップ
    2. **ファイル名+サイズ判定**: 保存先に同名ファイルが存在し、サイズが一致する場合はスキップ
    3. **ハッシュ判定**（オプション）: 設定で有効化した場合、ファイルのMD5ハッシュを計算して比較
  - **受け入れ条件**: 同一URLまたは同名+同サイズのファイルを検出した場合、ダウンロードをスキップし、ログに記録すること

#### 2.1.4 ファイル命名機能
- **FR-009**: HTML構造から取得した情報（ページタイトル、カテゴリ、日付など）を使用してファイル名を自動生成できること
  - **受け入れ条件**: テンプレート文字列（例: `{category}_{title}_{date}_{index}`）を使用してファイル名を生成できること
- **FR-010**: ユーザーが命名規則をカスタマイズできること
  - **受け入れ条件**: GUI上で命名テンプレートを編集し、設定ファイルに保存できること
- **FR-011**: ファイル名の重複を回避する仕組みを有すること
  - **重複回避方法**: 同名ファイルが存在する場合、末尾に連番（`_1`, `_2`など）を付与
  - **受け入れ条件**: 保存先に同名ファイルが存在する場合、自動的に連番を付与して保存すること

#### 2.1.5 保存機能
- **FR-012**: ユーザーが事前に指定したローカルフォルダにファイルを保存できること
  - **受け入れ条件**: フォルダ選択ダイアログで保存先を指定し、ファイルを正しく保存できること
- **FR-013**: フォルダ構造をHTML構造に基づいて自動生成できること（例：発注者別、カテゴリ別、日付別など）
  - **受け入れ条件**: 設定で有効化した場合、メタデータに基づいてサブフォルダを作成し、ファイルを分類保存できること

#### 2.1.6 スケジューリング機能
- **FR-016**: 定期的に自動実行できること
  - **実行方式**: アプリ起動中のみ定期実行（GUIアプリケーションとして常駐）
  - **スケジュール設定**: 
    - 実行間隔の指定（分単位、例: 60分ごと）
    - 実行時刻の指定（例: 毎日9:00）
  - **Windowsタスクスケジューラ連携**（将来拡張）:
    - PCログオン時に自動起動する機能は将来拡張として検討
    - 現時点では、アプリ起動中のみスケジュール実行をサポート
  - **受け入れ条件**: 設定した間隔または時刻に、アプリ起動中に自動的に検索・ダウンロードを実行できること
- **FR-017**: 実行ログを記録できること
  - **受け入れ条件**: 各実行の開始時刻、終了時刻、処理件数、エラー情報をログファイルに記録できること
- **FR-018**: 実行結果を通知できること（メール、ログファイルなど）
  - **受け入れ条件**: 実行完了時にログファイルに結果を記録し、GUI上で通知を表示できること

### 2.2 補助機能

#### 2.2.1 設定管理機能
- **FR-019**: 設定をファイル（YAML形式）に保存・読み込みできること
  - **受け入れ条件**: 設定をYAMLファイルに保存し、次回起動時に自動読み込みできること
- **FR-020**: 複数の設定プロファイルを管理できること
  - **受け入れ条件**: 複数の設定ファイルを切り替えて使用できること（将来拡張）

#### 2.2.2 ログ機能
- **FR-021**: 実行ログを記録できること
  - **FR-021-1**: ログ保存先を設定可能とすること
    - デフォルト: `./logs/app.log`
    - 設定ファイルで変更可能
  - **FR-021-2**: ログローテーション機能を有すること
    - 最大ファイルサイズ: 10MB（設定可能）
    - 世代数: 5世代（設定可能）
    - ローテーション方式: サイズベース（ファイルサイズが上限に達したらローテーション）
  - **受け入れ条件**: ログファイルが10MBに達した場合、自動的にローテーションし、最大5世代まで保持すること
- **FR-022**: エラーログを記録できること
  - **受け入れ条件**: エラー発生時にスタックトレースを含む詳細情報をログに記録できること
- **FR-023**: ログレベルを設定できること（DEBUG、INFO、WARNING、ERROR）
  - **受け入れ条件**: 設定ファイルでログレベルを変更し、該当レベルのログのみ出力できること

#### 2.2.3 UI機能
- **FR-024**: コマンドラインインターフェース（CLI）を提供すること（開発・デバッグ用）
  - **受け入れ条件**: 指定した設定ファイルを読み込み、1回の検索・ダウンロードを実行できること（開発・検証用）
    - 注: バックグラウンド常駐機能は将来拡張として検討
- **FR-025**: グラフィカルユーザーインターフェース（GUI）を提供すること（必須）
  - プログラミングに詳しくないユーザーでも操作できること
  - 直感的な操作が可能なこと
  - 設定をGUI上で行えること
  - ダウンロード進捗を視覚的に表示できること
  - 実行ログをGUI上で確認できること
  - **受け入れ条件**: GUI上で検索条件を設定し、ダウンロードを開始し、進捗とログを確認できること
- **FR-026**: 実行ファイル形式（.exe等）で配布できること
  - Python環境がなくても実行できること
  - インストール不要で実行できること（ポータブル版）
  - インストーラー版も提供できること（オプション）
  - **配布要件**:
    - 対象OS: Windows 10/11（64bit）
    - 配布形式: ポータブル版（zip展開）を基本
    - セキュリティソフトでの誤検知: 可能性があることを注記（PyInstaller使用による）
    - Pythonバージョン: 3.11.x（exe配布前提のためバージョン固定）
  - **受け入れ条件**: Windows 10/11（64bit）環境で、Python未インストールでも実行ファイルを起動できること

## 3. 非機能要件

### 3.1 パフォーマンス
- **NFR-001**: 大量のファイルをダウンロードする場合でも安定して動作すること
  - **受け入れ条件**: 100件以上のファイルをダウンロードしてもメモリリークなく動作すること
- **NFR-002**: ダウンロード処理の並列化を検討すること（オプション）
  - **受け入れ条件**: 設定で並列数を指定し、複数ファイルを同時ダウンロードできること（将来拡張）

### 3.2 セキュリティ
- **NFR-003**: ユーザー認証情報を平文で保存しないこと
  - **受け入れ条件**: 設定ファイルに認証情報を平文で保存しないこと

### 3.3 エラーハンドリング
- **NFR-005**: ネットワークエラー、ファイルシステムエラーなどに対して適切にエラーハンドリングを行うこと
  - **HTTPタイムアウト設定**:
    - 接続タイムアウト: 10秒（設定可能）
    - 読み込みタイムアウト: 60秒（設定可能）
    - **適用範囲**: すべてのHTTPリクエスト（ページ取得、ファイルダウンロード、POSTリクエスト等）に適用
    - 注: 回線が遅い環境でも無限待ちを避けるため、タイムアウト値は必須
  - **受け入れ条件**: ネットワークエラー、ファイルシステムエラー発生時に適切なエラーメッセージを表示し、処理を継続できること。タイムアウト時は適切にエラーとして記録すること
- **NFR-006**: エラー発生時も処理を継続できること（可能な限り）
  - **受け入れ条件**: 1件のファイルダウンロードに失敗しても、他のファイルのダウンロードを継続できること

### 3.4 保守性
- **NFR-007**: コードに適切なコメントを記述すること
  - **受け入れ条件**: 主要な関数・クラスにdocstringを記述すること
- **NFR-008**: 設定ファイルの形式を明確にドキュメント化すること
  - **受け入れ条件**: 設定ファイルの各項目について、READMEまたは設定ファイル例に説明を記載すること

## 5. データ要件

### 5.1 設定データ（YAML形式）

設定ファイルのスキーマを以下に示す。各項目の型と説明は実装設計書を参照。

```yaml
# 対象URL（検索画面）
target:
  url: string  # 検索画面URL（例: https://www.i-ppi.jp/.../Search.aspx?tab=4）

# フィルタ条件
filters:
  file_types: array[string]  # 拡張子リスト（例: [".pdf", ".xlsx"]）
  keywords: array[string] | string  # キーワード（配列または文字列）
  date_range:
    start: string | null  # YYYY-MM-DD形式
    end: string | null

# 保存先
save:
  local_dir: string  # ローカル保存先パス

# ファイル命名規則
naming:
  template: string  # テンプレート文字列（例: "{category}_{title}_{date}_{index}"）

# ダウンロード設定
download:
  retry:
    count: integer  # リトライ回数（デフォルト: 3）
    backoff: boolean  # 指数バックオフ使用（デフォルト: true）
  timeout:
    connect: integer  # 接続タイムアウト（秒、デフォルト: 10）
    read: integer  # 読み込みタイムアウト（秒、デフォルト: 60）
  part_file:
    on_cancel: string  # "keep" または "delete"（デフォルト: "keep"）

# スケジュール設定
schedule:
  enabled: boolean
  interval: integer | null  # 実行間隔（分単位）
  time: string | null  # 実行時刻（HH:MM形式）

# ログ設定
logging:
  level: string  # DEBUG, INFO, WARNING, ERROR（デフォルト: INFO）
  path: string  # ログファイルパス
  max_bytes: integer  # 最大ファイルサイズ（バイト、デフォルト: 10485760 = 10MB）
  backup_count: integer  # ローテーション世代数（デフォルト: 5）
```

**注**: 詳細なスキーマ定義とデフォルト値は実装設計書を参照すること。

### 5.2 ログデータ

#### 5.2.1 ログ出力フォーマット
- **通常ログ**: テキスト形式（人が読む形式）
  - フォーマット: `[YYYY-MM-DD HH:MM:SS] [LEVEL] [MODULE] - MESSAGE`
- **失敗ログ**: JSON Lines形式（1行1イベント、機械が読む形式）
  - 必須フィールド:
    - `url`: 対象URL
    - `status_code`: HTTPステータスコード（エラーの場合）
    - `error_type`: エラー種別（timeout, connection_error, http_error等）
    - `retry_count`: 再試行回数
    - `timestamp`: エラー発生時刻（ISO 8601形式）
    - `message`: エラーメッセージ

#### 5.2.2 ログデータの内容
- 実行日時
- ダウンロードしたファイル一覧
- エラー情報（上記JSON Lines形式）
- 実行結果サマリー（成功/失敗/スキップ件数、失敗理由別件数）

## 6. ユーザー要件

### 6.1 想定ユーザー
- 建設情報を定期的に収集する必要があるユーザー
- **プログラミングに詳しくないユーザーも含む**
- **Python環境を持たないユーザーも含む**
- GUI操作が可能なユーザー（Windows環境を想定）

### 6.2 ユーザー操作フロー（GUI版）
1. 初回起動
   - 実行ファイル（.exe）をダブルクリックして起動
   - GUI画面が表示される
2. 設定
   - GUI上でダウンロード条件を指定
     - 対象URLの入力
     - ファイルタイプの選択（チェックボックス等）
     - キーワードの入力
     - 日付範囲の指定
   - 保存先フォルダの選択（フォルダ選択ダイアログ）
   - 設定を保存
3. 実行
   - 「ダウンロード開始」ボタンをクリック
   - 進捗バーでダウンロード状況を確認
   - ログ画面で実行状況を確認
4. 結果確認
   - GUI上でダウンロード完了を確認
   - ログ画面で詳細を確認
   - 保存先フォルダを開いてファイルを確認

## 7. 制約事項

### 7.1 技術的制約
- ppi.jpのHTML構造が変更された場合、解析ロジックの修正が必要になる可能性がある
- ネットワーク接続が必要
- Windows 10/11（64bit）環境のみサポート

### 7.2 法的・倫理的制約
- ppi.jpの利用規約を遵守すること
- robots.txtを確認し、クローリングが許可されているか確認すること
- 過度なリクエストを送信しないこと（レート制限の考慮）
  - **レート制限の目安**: 1〜2 req/sec（429エラーが発生した場合は自動的に待機）
  - **User-Agent明示**: ツール名/連絡先をUser-Agentに含める（任意）
    - **実装ルール**: `ppi-file-downloader/2.1 (+contact: internal)` のような固定文字列を使用（一貫性のため）
  - **社内利用形態**: 社内端末での利用形態（ログイン有無、規約の禁止条項）を確認すること
- **対応範囲の明確化**: 本ツールはログインを必要としない範囲を対象とする
  - ログインが必要な機能や、認証が必要なファイルへのアクセスは対象外
  - ログイン機能が必要になった場合は、認証方式（ID/PW/OAuth/CAPTCHA等）を別途検討する

## 9. 受け入れ試験（Acceptance Test）

本ツールの承認時に実施する受け入れ試験項目を以下に示す。

### 9.1 基本機能の受け入れ試験

- **AT-01: 条件指定によるファイル取得**
  - **試験内容**: 
    1. GUI上で検索条件を設定（ファイルタイプ、キーワード、日付範囲等）
    2. ダウンロードを実行
    3. 取得可能な添付ファイルが保存先に保存されることを確認
    4. 実行結果サマリーの件数が実際の保存件数と一致することを確認
  - **合格基準**: 
    - 設定した条件に一致するファイルが正しく保存されること
    - サマリーの成功件数が保存ファイル数と一致すること
    - 失敗したファイルはログに記録され、サマリーに反映されること

- **AT-02: 429エラー時の待機動作**
  - **試験内容**: 
    1. 429エラーが発生する状況を模擬（模擬方法は以下いずれか）
       - テスト用に意図的に高頻度アクセス（ただし規約に抵触しない範囲）
       - ローカルの簡易HTTPサーバーで 429 を返すモックを用意
       - requests のアダプタ/モック（responses等）で 429 + Retry-After を再現
    2. `Retry-After`ヘッダーが存在する場合はその値に従って待機することを確認
    3. `Retry-After`ヘッダーが存在しない場合は指数バックオフで待機することを確認（最大60秒）
    4. 待機後にリトライが実行されることを確認
  - **合格基準**: 
    - 429エラー時に適切な待機時間を確保すること
    - `Retry-After`ヘッダーを優先的に使用すること
    - 待機後にリトライが実行され、成功する場合はファイルが保存されること

- **AT-03: 実行中のキャンセル処理**
  - **試験内容**: 
    1. ダウンロード処理を開始
    2. 処理中にキャンセルボタンをクリック
    3. 進行中の通信が中断されることを確認
    4. `.part`ファイルの扱いが設定に従うことを確認（残す/削除）
    5. GUIが固まらず、正常に終了することを確認
  - **合格基準**: 
    - キャンセル操作後、通信が即座に中断されること
    - `.part`ファイルが設定通りに処理されること（残す設定の場合は残存、削除設定の場合は削除）
    - GUIが応答し続け、エラーなく終了すること
    - ログにキャンセル情報が記録されること

- **ppi.jp**: 建設情報サービスを提供するWebサイト
