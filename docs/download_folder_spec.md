# ダウンロードフォルダー仕様

## 1. この文書の位置付け

本書は、ippi-downが取得した文書の保存先、フォルダー名、ファイル名、履歴、一時ファイル、旧構成との互換性を定める正本仕様です。README、要件定義書、実装設計書と内容が異なる場合は、本書を保存レイアウトの規範とします。

検索条件、通信、スケジュールの発火方法そのものは対象外です。ただし、実行種別や取得メタデータが保存先へ影響する規則は本書で定めます。

## 2. 用語

| 用語 | 意味 |
|---|---|
| データルート | `save_paths.local`で指定する、すべての取得文書をまとめる基準フォルダー |
| 実行ルート | 通常実行または1つの定期実行設定に割り当てる、履歴を共有する単位 |
| 相対保存先 | 実行ルートから完成ファイルまでの相対パス |
| 発注機関階層 | 大分類、中分類、小分類、細分類のうち、対象サイトから確定できた階層 |
| 文書区分 | 公開文書テーブル上の区分を保存用の3区分へ変換した値 |
| 固定保存キー | 定期実行設定へ一度だけ発行する`S001`形式の識別子 |
| 文書改訂 | 本書の更新番号`document_revision`。保存互換性とは独立して管理する |
| レイアウト版 | 設定の`save_paths.layout_version`。保存先と履歴互換性の契約を表す |

## 3. 現行レイアウトv4

### 3.1 データルートの解決

`save_paths.local`が絶対パスならその場所を使用します。相対パスなら、ソース実行時はプロジェクトルート、exe実行時はexeの配置場所を基準に解決します。PowerShellやコマンドプロンプトの現在位置は基準にしません。

`normal_folder`と`scheduled_folder`は、安全化後かつWindowsの大文字小文字非依存比較でも異なる名前でなければなりません。

### 3.2 実行種別と実行ルート

| 起動方法 | 実行種別 | 実行ルート |
|---|---|---|
| GUIの「ダウンロード開始」 | 通常 | `<データルート>/<検索対象>/<normal_folder>` |
| `--run-once` | 通常 | `<データルート>/<検索対象>/<normal_folder>` |
| 旧互換の`--background` | 通常 | `<データルート>/<検索対象>/<normal_folder>` |
| `--scheduled-run` | 定期 | `<データルート>/<検索対象>/<scheduled_folder>/<schedule_storage_folder>` |

検索対象フォルダーは`工事の検索（入札の経過）`または`業務の検索（入札の経過）`で、設定変更できない保存契約です。既定値は`normal_folder: 01_通常ダウンロード`、`scheduled_folder: 02_定期実行`です。v4の定期実行で固定保存フォルダーがない場合は、通常側へ混在させず設定エラーとします。

### 3.3 完成ファイルのパス

通常実行は次の構成です。

```text
<データルート>\
└─ <検索対象>\
   └─ 01_通常ダウンロード\
      └─ [99_分類未解決\]<確定または取得できた発注機関階層>\<案件名>\<文書区分>\<ファイル名>
```

定期実行は次の構成です。

```text
<データルート>\
└─ <検索対象>\
   └─ 02_定期実行\
      └─ S001_<設定の初回名称>\
         └─ [99_分類未解決\]<確定または取得できた発注機関階層>\<案件名>\<文書区分>\<ファイル名>
```

角括弧内は必要な場合だけ追加します。発注機関の大・中・小・細分類のうち存在しない階層は、空の代替フォルダーを作らず省略します。隣接する階層名がWindowsの大文字小文字非依存比較で同じ場合は1階層へまとめます。

通常実行の例です。

```text
downloads\工事の検索（入札の経過）\01_通常ダウンロード\国の機関\国土交通省\東北地方整備局\山形河川国道事務所\国道１３号_金山第二トンネル工事\01_入札公告等\入札公告_20260730_1200.pdf
```

分類を確定できず、担当部・事務所名だけ取得できた例です。

```text
downloads\工事の検索（入札の経過）\01_通常ダウンロード\99_分類未解決\国土交通省\山形河川国道事務所\工事名不明\99_区分不明\文書_更新日時不明_18.pdf
```

## 4. Webサイト情報からフォルダーへの変換

### 4.1 発注機関

- 公式[「発注機関複数選択」画面](https://www.i-ppi.jp/IPPI/SearchServices/Web/Multi/SearchHachu.aspx?type=koji&clear_flg=false)のツリーを高速化用の分類カタログとして、大分類～小分類の表示名、コード、親子関係を取得します。カタログはプロセス内メモリだけに保持し、ディスクには保存しません。
- 細分類の取得、分類カタログとの照合、検索送信値の最終検証、案件検索、詳細ページ解析、公開文書の取得には`tab=4`の「発注機関（リスト検索）」を使用します。
- 保存時は、詳細ページ情報と分類マスターから一意に解決した階層を優先し、次に登録済み検索条件の階層を使用します。
- 一意に解決できない場合は推測せず、先頭へ`99_分類未解決`を置き、その後に取得できた発注機関名や担当部・事務所名を並べます。
- 表示名が取得できた階層だけを、大分類、中分類、小分類、細分類の順に使用します。

### 4.2 工事名

詳細ページの工事名称を使用します。取得できない場合は案件メタデータの名称、それもない場合は`工事名不明`を使用します。

### 4.3 文書区分

| Web側の区分 | 保存フォルダー |
|---|---|
| `入札公告等`または入札公告を示す区分 | `01_入札公告等` |
| `入札経過・その他`、`入札の経過`または入札経過を示す区分 | `02_入札経過・その他` |
| 未取得、未知の区分 | `99_区分不明` |

未知の区分を既知区分へ推測して保存しません。

## 5. ファイル名

### 5.1 命名テンプレート

既定値は`{document_name}_{document_updated_at}`です。更新日時は日本標準時の`YYYYMMDD_HHmm`へ正規化します。更新日時がない、または解析できない場合は`更新日時不明_<document_id>`を使用し、現在時刻や公告日時で代用しません。

文書IDは、文書メタデータ、URLの`BunshoKanriId`、URLのSHA-256先頭8桁の順に決定します。文書名がない場合は取得元ファイル名の拡張子を除いた名前、最後に`文書`を使用します。テンプレート結果に元文書の拡張子がなければ自動的に追加します。

使用可能な変数は次の17個です。

```text
{filename} {file_type} {category} {title} {date} {index}
{daibunrui} {chubunrui} {shoubunrui} {saibunrui} {koji_name}
{document_name} {document_updated_at} {document_id}
{document_status} {document_expires_at} {document_section}
```

空のテンプレート、構文エラー、未知の変数は設定保存時に拒否します。旧既定値`{category}_{title}_{date}_{index}`だけは読み込み時に現行既定値へ移行し、それ以外の利用者定義テンプレートは変更しません。

### 5.2 同名衝突

- 同一実行内で異なるURLが同じ保存先を要求した場合、衝突した文書へ安定した`_<document_id>`を追加します。
- 文書ID付き候補にも履歴で説明できない既存ファイルがある場合だけ、`_1`、`_2`の連番を使用します。探索上限は1000です。
- 有効な履歴と一致するファイルは検証後に再利用し、強制再取得時は検証済み`.part`から同じ正式名を置換します。
- 既存ファイルを根拠なく上書きしません。

## 6. Windowsパスの安全化

各パス要素には次の変換を順に適用します。

1. 制御文字と`< > : " / \\ | ? *`を`_`へ置換する。
2. 先頭と末尾の空白・ピリオドを除去する。
3. 連続する空白とアンダースコアを1つの`_`へまとめる。
4. 空になった要素を`untitled`へ置換する。
5. `CON`、`PRN`、`AUX`、`NUL`、`COM1`～`COM9`、`LPT1`～`LPT9`に該当する名前の先頭へ`_`を付ける。
6. 解決後の保存先が実行ルート内にあることを確認し、ルート外パスを拒否する。

完成ファイルの絶対パスは240文字以内とします。超える場合はフォルダー名とファイル名を均等に短縮し、元の値のSHA-256先頭8桁を付けます。ファイルの拡張子は維持します。データルートや実行ルート自体が長すぎて安全に短縮できない場合は、利用者へ短いデータルートを指定するようエラーを返します。

## 7. 一時ファイルとダウンロード履歴

### 7.1 一時ファイル

通信中またはHTMLからPDFへの変換中は、完成ファイルと同じフォルダーの`.part`へ書き込みます。内容検証後にだけ正式名へ原子的に置換します。失敗またはキャンセル時は処理中の`.part`だけを削除し、既存の正常ファイルを保持します。

### 7.2 履歴の配置

| レイアウト | 履歴ファイル |
|---|---|
| v4通常実行 | `<データルート>/<検索対象>/<normal_folder>/.ippi-download-history.jsonl` |
| v4定期実行 | `<データルート>/<検索対象>/<scheduled_folder>/<schedule_storage_folder>/.ippi-download-history.jsonl` |
| v3通常実行 | `<データルート>/<normal_folder>/.ippi-download-history.jsonl` |
| v3定期実行 | `<データルート>/<scheduled_folder>/<schedule_storage_folder>/.ippi-download-history.jsonl` |
| v2 | `<save_paths.local>/.ippi-download-history.jsonl` |

検索対象、通常実行、各定期実行設定は別々の履歴を持ちます。履歴は追記形式で、取得元URL、意図した相対保存先、実際の保存先、期待形式、状態、処理モード、サイズ、SHA-256、日時、文書情報、検索対象、layout版を保持します。v3以降では発注機関階層、実行種別、定期実行の固定保存キーも保持します。

履歴の再利用キーは、取得元URL、現在の正規化済み相対保存先、期待形式の組み合わせです。候補ファイルのサイズ、SHA-256、PDF署名・終端またはOOXML構造、公開元の更新日時を再検証します。同一キーの最新状態が`FAILED`または`CANCELLED`なら、それより古い成功を使いません。

現行命名へ移行した文書について、有効な旧命名履歴が見つかった場合は既存ファイルを移動・改名・コピーせず、その実ファイルを再利用したことを現行保存先の別名履歴として記録できます。ただし異なるlayout版または異なる検索対象の履歴を新階層の別名として再利用しません。

### 7.3 分類診断と保存済みファイルの手動再分類

検索中は案件ごとに、確定した発注機関階層、解決状態、解決方法、固定理由コード、日本語理由、担当部・事務所名を保持します。「案件・文書内訳」では発注機関階層、分類状態、分類理由と、実行ルートからの保存予定フォルダーを表示します。集計には分類確定案件数と`99_分類未解決`になる案件数を分けて表示し、`分類未解決`で絞り込めます。

新しい検索・ダウンロードで保存先分類を確定できなかった場合は、次のいずれかの固定理由コードを記録します。表示名だけから別の機関を推測しません。

| 理由コード | 意味 |
|---|---|
| `AGENCY_SELECTION_MISSING` | 発注機関が検索条件にない |
| `AGENCY_DETAIL_MISSING` | 詳細ページに担当部・事務所情報がない |
| `AGENCY_FINE_NOT_FOUND` | 細分類候補に一致しない |
| `AGENCY_FINE_AMBIGUOUS` | 細分類候補が複数一致する |
| `AGENCY_OFFICE_CONFLICT` | 選択条件と詳細ページ情報が競合する |
| `AGENCY_CATALOG_FETCH_FAILED` | 分類候補を取得できない |
| `AGENCY_PATH_INCOMPLETE` | 階層が途中までしか確定していない |

確定時は`AGENCY_SELECTED`、`OFFICE_LABEL_MATCH`、旧履歴を厳密照合した場合は`LEGACY_ID_MATCH`を根拠として記録します。

既存ファイルは検索や設定保存だけでは移動しません。利用者が設定画面の「データルート」から「保存済みファイルを再分類...」を開いたときだけ、通常実行と各定期実行のv3/v4履歴を読み、現在ファイルをサイズ、SHA-256、PDFまたはOOXML構造で再検証して候補を作ります。v4では工事と業務を別々の実行ルートとして走査します。プレビューには選択、実行区分、定期実行設定、案件、文書、現在位置、移動先、理由、可否を表示します。利用者が再分類可能な候補を選び、確認画面で実行を承認するまでファイルは変更しません。

再分類は次の安全条件に従います。

- 工事と業務、通常実行と定期実行、異なる定期設定の間では移動せず、同じ実行ルート内の`99_分類未解決`から確定階層へだけ移動します。
- 移動元が履歴と一致しない、階層を一意に解決できない、移動先に異なる内容がある場合は変更しません。
- 移動先がなければ同一ファイルシステム内で移動します。移動先に同じサイズ、SHA-256、形式の検証済みファイルがある場合は、その移動先を正本として履歴化します。この場合、`99_分類未解決`側の旧ファイルは削除せず保持し、プレビューと結果へ警告を表示します。
- 1件ごとに再検証し、処理ジャーナルを残してからファイルと履歴を更新します。履歴確定前の失敗は元の場所へ戻し、確定後の中断は次回起動または再スキャン時に後処理を回復します。
- ダウンロード、定期実行、別の再分類が実行中または順番待ちの場合は`RECLASSIFICATION_RUN_LOCKED`として開始しません。進捗を表示し、キャンセル要求は候補間と安全な処理境界で確認します。
- v2履歴、履歴に分類根拠がないファイル、履歴外のファイルを自動移動しません。対象外のファイルはプレビューに理由付きで残します。

完了画面は、移動、移動先の正本化（旧ファイル保持）、競合、不正、対象外・スキップ、失敗、キャンセルを別件数で表示します。完全な診断は`logs/app.log`に記録します。

## 8. 定期実行フォルダーの識別

- 新規登録時に、削除済み番号を再利用しない単調増加の`S001`、`S002`形式で固定保存キーを発行します。
- 保存フォルダーは`<固定保存キー>_<設定の初回名称>`です。初回名称はWindows用に安全化します。
- 表示名や条件を編集しても、固定保存キーと保存フォルダーを変更しません。
- 複製時は新しい固定保存キーと保存フォルダーを発行します。
- 別配置から明示的に取り込む場合は、検証済みのデータルート、固定保存キー、保存フォルダーを引き継ぎます。取得済み文書や履歴を新しい配置へコピーせず、同じ実行ルートを継続して使用します。
- 無効化または削除しても、取得済み文書、履歴、保存フォルダーを移動・改名・削除しません。
- 登録台帳はキーの形式と重複を検証し、スナップショットの指紋に保存先識別情報を含めます。

## 9. 旧レイアウトv2・v3

`layout_version`がない設定はv2として読み込みます。v2では通常・定期を分離せず、`save_paths.local`自体を実行ルートとします。

```text
<save_paths.local>\<取得できた大_中_小_細_工事名>\<ファイル名>
```

v3は`<データルート>/<normal_folder>`と`<データルート>/<scheduled_folder>/<schedule_storage_folder>`を使用し、工事と業務を最上位では分離しません。v3からv4へは設定画面の確認後に切り替え、既存文書と履歴を移動、改名、削除しません。新しい対象別ルートでは旧履歴を再利用しないため、同じ文書が一度再取得される場合があります。現行アプリが受理するlayout版は`2`、`3`、`4`です。

## 10. 仕様変更と版管理

### 10.1 `document_revision`を更新する変更

説明、例、Web要素の取得方法、セレクター、送信用コード、既存パスへ対応付ける表示名を更新するときは、本書の`document_revision`と変更履歴を更新します。保存される相対パスと履歴互換性が変わらなければ`layout_version`は維持します。

### 10.2 新しい`layout_version`が必要な変更

次のいずれかに該当する場合は、新しい整数のlayout版、設定の既定値、履歴互換規則、移行方針を同じ変更で定義します。

- 同じ入力文書の相対保存先が変わる。
- 実行ルート、発注機関階層、工事名、文書区分の構造や名称が変わる。
- 安全化、短縮、衝突回避の結果が変わる。
- 履歴キーまたは旧履歴を再利用できる条件が変わる。
- 通常実行と定期実行の分離方法が変わる。

既存設定を新しい版として黙って解釈し直しません。v3からv4への切替はGUIで既存データを移動しないことと再取得の可能性を表示し、利用者が承認した場合だけ設定と新しい定期実行スナップショットへ固定します。

### 10.3 変更時チェックリスト

1. 変更理由を「Webサイト変更」「利用者要望」「不具合修正」のいずれかで記録する。
2. 同じ入力に対する変更前後の完全な相対パス例を示す。
3. 履歴再利用、既存ファイル、定期実行の固定保存フォルダーへの影響を判定する。
4. 自動移行の有無を明記し、移動・改名・削除を行う場合は別途明示承認を得る。
5. 保存済みHTML fixture、パス安全化、履歴、ソース／exe配布のテストを更新する。
6. 本書、README、要件定義、実装設計の参照と変更履歴を更新する。
