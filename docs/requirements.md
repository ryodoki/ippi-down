# ippi-down 要件定義書（レビュー版）

## 1. プロジェクト概要

### 1.1 プロジェクト名
ippi-down

### 1.2 目的
建設情報サービス「i-ppi.jp」のWebサイトから、ユーザーが指定した条件に基づいてファイルを自動的にダウンロードし、指定したフォルダに整理して保存する自動化ツールを開発する。

### 1.3 対象サイト
- **入口ページ**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Index.htm
- **工事の発注機関高速カタログ**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Multi/SearchHachu.aspx?type=koji&clear_flg=false
- **業務の発注機関高速カタログ**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Multi/SearchHachu.aspx?type=gyomu&clear_flg=false
- **工事検索画面**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Search/Search/Search.aspx?tab=4
- **業務検索画面**: https://www.i-ppi.jp/IPPI/SearchServices/Web/Search/Search/Search.aspx?tab=7
- サイト名: 建設情報サービス

保存先、命名、履歴、旧構成との互換性の詳細は、正本である[ダウンロードフォルダー仕様](download_folder_spec.md)を参照すること。

## 2. 機能要件

### 2.1 コア機能

#### 2.1.1 HTML構造解析機能
- **FR-001**: 対象サイトのWebページのHTML構造を解析できること
  - **対象ページ**: 入口ページ（Index.htm）、対象別発注機関複数選択画面、工事検索（`tab=4`）、業務検索（`tab=7`）
  - **受け入れ条件**: 検索ページのHTMLを取得し、フォーム要素、ドロップダウン、テーブル構造を正しく解析できること
- **FR-002**: ページ内のファイルリンク（PDF、Excel、Wordなど）を検出できること
  - **受け入れ条件**: 詳細表示（遷移またはポストバック）後のHTMLまたはダウンロード応答から、添付ファイル取得に必要なURL/POSTパラメータを特定し、保存できること
    - 注: 現時点では`dgrKokoku`および`dgrKeika`テーブル、`KokaiBunshoServlet`などのパターンを想定しているが、サイト構造変更時は解析ロジックの調整が必要
  - **対応ファイル種別**: 
    - 拡張子あり: `.pdf`, `.xlsx`, `.docx`, `.xls`, `.doc`, `.jpg`, `.png`
    - 拡張子なし: Content-TypeヘッダーまたはContent-Dispositionヘッダーから判定
    - ZIPファイル: 必要に応じて展開処理を検討（将来拡張）
- **FR-003**: HTMLの階層構造（ページタイトル、発注機関、案件名（文字列検索）、カテゴリ、日付など）を抽出できること
  - **受け入れ条件**: 検索結果ページまたは詳細表示ページから、発注機関名、工事／業務名称、公告日、開札日、契約日などのメタデータを抽出できること
  - 発注機関の全階層は対象別に動的取得し、工事の送信値検証・検索・文書取得は`tab=4`、業務は`tab=7`を使用すること
  - 候補更新は起動時・対象の初回利用時・手動再読込に限定し、成功時に全置換すること。削除値や最新性未確認の指定値で検索・保存・定期実行を行わないこと
    - 注: メタデータの抽出方法はサイト構造に依存するため、構造変更時は解析ロジックの調整が必要

#### 2.1.2 条件指定機能
- **FR-004**: ユーザーが事前にダウンロード条件を設定できること
  - 対象ページURLの指定
  - ファイルタイプのフィルタリング（拡張子指定）
  - 検索対象、発注機関、案件名
  - キーワード検索条件
  - 日付範囲の指定
  - その他のカスタム条件
  - **受け入れ条件**: GUI上で検索条件を設定し、設定ファイル（YAML）に保存・読み込みできること

#### 2.1.3 自動ダウンロード機能
- **FR-005**: 指定した条件に一致するファイルを自動的にダウンロードできること
  - **受け入れ条件**: 指定条件で検索し、添付が存在し、かつ取得可能なものは全件保存する。取得不能なもの（サイト側の不具合、認証切れ、アクセス権限なし等）は失敗としてログに残し、実行結果サマリーに件数を出力すること
  - **失敗時の記録項目**:
    - HTTPステータスコード
    - 例外種別（タイムアウト、接続エラー、HTTPエラー等）
    - 対象URL
    - 再試行回数
  - **実行結果サマリー**: 失敗理由別件数を出力すること
    - ネットワークエラー（タイムアウト、接続エラー）
    - 429（Too Many Requests）
    - 5xx（サーバーエラー）
    - 4xx（クライアントエラー）
    - その他
- **FR-006**: ダウンロード進捗状況を表示できること
  - **受け入れ条件**: GUI上で進捗バー、成功/失敗/スキップ件数をリアルタイム表示できること
- **FR-006-1**: ダウンロード処理をユーザーがキャンセルできること
  - **一時ファイルの扱い**:
    - ダウンロード中は常に `.part` 拡張子で保存し、成功時にリネーム
    - キャンセル時は `.part` ファイルを残す/削除する（設定で選択可能）
    - 推奨: `.part` を残す（次回実行時の判定に使用可能）
  - **`.part` ファイルの再開について**:
    - `.part` は次回実行時に「削除」または「上書き再取得」を基本とする
    - HTTP Range による途中再開（レジューム機能）は将来拡張とする
  - **受け入れ条件**: キャンセル操作後、進行中の通信を中断し、安全に処理を終了すること。`.part` ファイルの扱いは設定に従うこと。GUIが固まらないこと
- **FR-007**: ダウンロード失敗時のリトライ機能を有すること
  - **リトライ方針**:
    - リトライ回数: 3回（設定可能）
    - リトライ間隔: 指数バックオフ（1秒、2秒、4秒）
    - 対象エラー: タイムアウト、5xxエラー、429（Too Many Requests）
    - 対象外エラー: 4xx（クライアントエラー、404など）、認証エラー
  - **429エラー時の待機戦略**:
    - `Retry-After`ヘッダーが存在する場合は、その値に従って待機
    - `Retry-After`ヘッダーが存在しない場合は、指数バックオフを使用（最大待機時間: 60秒）
  - **受け入れ条件**: ネットワークエラー時に自動リトライし、3回失敗した場合のみエラーとして記録すること。429エラー時は適切な待機時間を確保すること
- **FR-008**: 既にダウンロード済みのファイルをスキップできること（重複回避）
  - 履歴キーは取得元URL、現在の正規化済み相対保存先、期待形式の組み合わせとする
  - 最新の実取得結果が成功で、保存済みファイルのサイズ、SHA-256、ファイル構造、公開元更新日時を再検証できた場合だけ再利用する
  - **受け入れ条件**: 不正または失敗後の履歴はスキップに使用せず、既存ファイルを保持したまま再取得へ進むこと

#### 2.1.4 ファイル命名機能
- **FR-009**: HTML構造から取得した情報（ページタイトル、カテゴリ、日付など）を使用してファイル名を自動生成できること
  - **受け入れ条件**: テンプレート文字列（例: `{category}_{title}_{date}_{index}`）を使用してファイル名を生成できること
- **FR-010**: ユーザーが命名規則をカスタマイズできること
  - **受け入れ条件**: GUI上で命名テンプレートを編集し、設定ファイルに保存できること
- **FR-011**: ファイル名の重複を回避する仕組みを有すること
  - **重複回避方法**: 異なる文書が同じ保存先になる場合は安定した文書IDを付け、それでも履歴で説明できない物理衝突がある場合だけ連番を使用する
  - **受け入れ条件**: 同じ入力から同じ名前を再現でき、既存ファイルを根拠なく上書きしないこと

#### 2.1.5 保存機能
- **FR-012**: ユーザーが事前に指定したローカルフォルダにファイルを保存できること
  - **受け入れ条件**: フォルダ選択ダイアログで通常実行と定期実行をまとめるデータルートを指定し、ファイルを正しく保存できること
- **FR-013**: 保存構成v4では検索対象、実行種別、発注機関、案件、文書区分に基づく固定フォルダ構造を自動生成できること
  - 完全なパス文法と変換規則は[ダウンロードフォルダー仕様](download_folder_spec.md)に従うこと
  - **受け入れ条件**: 工事と業務をデータルート直下で分離し、その下で通常実行と定期実行を分離すること。同じ入力は決定的な階層へ保存され、Windows上で同じになるルート名を拒否すること
- **FR-013-1**: 旧保存構成との非破壊互換性を維持すること
  - `layout_version`がない旧設定はv2として`save_paths.local`自体を保存先に使用すること
  - 旧ファイルと履歴を自動で移動、改名、削除しないこと
  - v3では旧flat保存履歴を、v4では異なるlayout版または検索対象の履歴を新しい階層の別名として再利用しないこと

#### 2.1.6 スケジューリング機能
- **FR-016**: 定期的に自動実行できること
  - **実行方式**: Windowsタスクスケジューラ（GUI終了後も実行）
  - **スケジュール設定**: 毎日、毎週（曜日）、毎月（1～28日）、実行時刻
  - **実行条件**: `InteractiveToken`で登録した同じWindowsユーザーがログオン中（画面ロック中は可、サインアウト中は不可）、ネットワーク利用可能、同一設定の多重起動拒否、異なる設定はFIFOで直列実行
  - **実行漏れと電源**: `StartWhenAvailable`で次回利用可能時に1回だけ補完でき、`WakeToRun`でスリープ解除の有無を設定すること
  - **実行上限**: キュー待機2時間、実処理2時間、Windowsタスク全体4時間
  - **検索条件**: 登録時に検証済みの不変スナップショットを作成し、画面上の未保存値を直接参照しない
  - **保存先**: 登録時に`S001`形式の固定保存キーと保存フォルダを発行し、表示名変更では改名せず、複製時は新しいキーを発行する
  - **タスク所有**: 配置単位の`config/schedule-instance-id`をtask namespace IDとし、別配置のWindowsタスクを自配置の登録として更新・削除しない
  - **全体調整**: ユーザー単位の`%LOCALAPPDATA%\ippi-down\install-id`はcoordination IDとしてFIFO・プロセス間排他だけに使用し、タスク所有IDと分離する
  - **配置変更**: `config/install-location.json`の確認済み位置と現在位置を比較し、フォルダー一式の移動は利用者の確認後に同じtask namespaceとして追従する。旧配置が残っていても旧パスを正常扱いせず、exe単体を管理ファイルなしで別フォルダーへコピーした場合は新しい配置として扱う
  - **配置変更時の保存先**: 旧配置内に包含される保存先・ログだけを現在配置基準の相対パスへ変換し、外部保存先、旧snapshot、既存文書、履歴、ログ、旧フォルダーは変更しない
  - **配置変更の中断回復**: 変更開始前に`config/installation-relocation-journal.json`を原子的に保存し、強制終了後は非GUI実行を停止する。次回GUI確認時に同じ旧・新ルートで残処理を再開し、commit後だけjournalを削除する
  - **受け入れ条件**: 同じWindowsユーザーがログオン中ならGUIを閉じた状態でも登録時刻に実行でき、自配置の移動・欠落・定義差分と別配置のタスクを区別して診断でき、配置確認が未完了ならダウンロードと設定保存を停止すること
- **FR-016-1**: 別配置の定期実行設定を明示操作で安全に取り込めること
  - 移行元`config`を利用者が選択し、台帳、封印済みスナップショット、ID、保存先、Windowsタスクを検証してからプレビューすること
  - 移行先に同名設定がある場合は1～80文字の一意な新名称を明示入力させ、黙った上書きや自動改名を行わないこと
  - 検証済みの対象だけを移行先へ一時無効で作成し、旧タスクを無効化してから、移行元の有効／無効状態を現在のexe用の移行先へ引き継ぐこと
  - 移行先の状態確定後に移行元を`MIGRATED_OUT`として無効化し、旧タスクを削除すること。削除失敗時は旧タスクの無効状態を維持し、`EXTERNAL_TASK_CLEANUP_PENDING`を返すこと
  - 同じ論理設定の実行履歴は現在の履歴へ安全に統合し、統合失敗は`EXTERNAL_HISTORY_IMPORT_FAILED`として所有権移行の成功と分離すること。元の履歴ファイルは削除しないこと
  - 台帳または検証可能なスナップショットがない孤立タスクは取り込まず、利用者確認後の解除だけを許可すること
  - **受け入れ条件**: 自動移行や推測による所有権移転を行わず、選択した設定だけを現在のexe用として取り込み、既存文書・履歴を移動、改名、削除しないこと
- **FR-017**: 実行ログを記録できること
  - **受け入れ条件**: 各実行の論理設定ID、スナップショットID、表示名、予定／開始／終了、起動種別、キュー待機時間、結果、件数、再試行、理由コード、終了コードを`logs/schedule-runs.jsonl`へ記録できること
- **FR-018**: 定期設定ごとに最終実行結果のWindows通知方針を選択できること
  - 通知方針は`off`、`important_only`、`all_results`、`failures_only`とする
  - 既存設定と旧スナップショットは`off`、GUIで作る新規設定は`important_only`を既定とする
  - `important_only`は新規保存、失敗、キャンセル、設定不正、時間超過などだけを通知し、全件保存済みと正常な該当なしは通知しない
  - 再試行途中やFIFO受付時は通知せず、最終履歴の保存後に`run_id`ごとに1回だけ通知する
  - 通知には設定名、最終結果、新規・保存済み・失敗件数、先頭理由コードだけを含め、検索条件、URL、Cookie、保存先を含めない
  - 通知失敗やWindowsの集中モードはダウンロード結果・終了コードを変更しない
  - **受け入れ条件**: 常駐tray processや追加通知依存なしで短命なWindows通知を行い、通知できない場合も履歴とファイルログから同じ最終結果を確認できること

### 2.2 補助機能

#### 2.2.1 設定管理機能
- **FR-019**: 設定をファイル（YAML形式）に保存・読み込みできること
  - **受け入れ条件**: 設定をYAMLファイルに保存し、次回起動時に自動読み込みできること
- **FR-020**: メイン画面全体の任意設定プロファイルを管理できること
  - **受け入れ条件**: 定期実行設定とは別に、複数の一般設定ファイルを切り替えて使用できること（将来拡張）

#### 2.2.2 ログ機能
- **FR-021**: 実行ログを記録できること
  - **FR-021-1**: ログ保存先を設定可能とすること
    - デフォルト: `./logs/app.log`
    - 設定ファイルで変更可能
  - **FR-021-2**: ログローテーション機能を有すること
    - 最大ファイルサイズ: 10MB（設定可能）
    - 世代数: 5世代（設定可能）
    - ローテーション方式: サイズベース（ファイルサイズが上限に達したらローテーション）
  - **受け入れ条件**: ログファイルが10MBに達した場合、自動的にローテーションし、最大5世代まで保持すること
- **FR-022**: エラーログを記録できること
  - **受け入れ条件**: エラー発生時にスタックトレースを含む詳細情報をログに記録できること
- **FR-023**: ログレベルを設定できること（DEBUG、INFO、WARNING、ERROR）
  - **受け入れ条件**: 設定ファイルでログレベルを変更し、該当レベルのログのみ出力できること

#### 2.2.3 UI機能
- **FR-024**: コマンドラインインターフェース（CLI）を提供すること（開発・デバッグ用）
  - **受け入れ条件**: 指定した設定ファイルを読み込み、1回の検索・ダウンロードを実行できること（開発・検証用）
    - 注: 常駐バックグラウンドプロセスは提供せず、定期実行はWindowsタスクが必要時だけ起動する
- **FR-025**: グラフィカルユーザーインターフェース（GUI）を提供すること（必須）
  - プログラミングに詳しくないユーザーでも操作できること
  - 直感的な操作が可能なこと
  - 設定をGUI上で行えること
  - ダウンロード進捗を視覚的に表示できること
  - 実行ログをGUI上で確認できること
  - 定期実行の通常一覧と「管理外の旧Windowsタスク（通常の保存条件とは別管理）」を別枠で表示すること
  - 管理外タスクはメイン画面の通常一覧へ混在させず、件数だけを集計し、通常の編集・修復・実行操作を許可しないこと
  - 旧設定の検査と取り込み、外部タスクの確認付き解除をバックグラウンドで行い、処理中もTkメインスレッドを停止しないこと
  - 管理外枠では「旧設定を取り込む...」と「選択した外部タスクを解除」を提供し、取り込みpreviewへ設定名、有効状態、実行予定、実効保存先、可否、Windowsタスク名、診断を表示すること
  - 管理対象の定期実行は、実行中・順番待ち・再試行待機中でも複製、編集、削除、有効化／無効化できること。開始済み・待機済みの実行は旧スナップショットを使い続けることを操作前に示し、「今すぐ実行」は重複開始を防ぐこと
  - 小さい作業領域でも定期実行の操作欄と設定画面の保存・キャンセルへ到達できること。操作ボタンは幅に応じて折り返し、一覧・登録内容・履歴は必要に応じてスクロールできること
  - **受け入れ条件**: GUI上で検索条件を設定し、ダウンロードを開始し、進捗とログを確認できること
- **FR-026**: 実行ファイル形式（.exe等）で配布できること
  - Python環境がなくても実行できること
  - インストール不要で実行できること（ポータブル版）
  - インストーラー版も提供できること（オプション）
  - **配布要件**:
    - 対象OS: Windows 10/11（64bit）
    - 配布形式: ポータブル版（zip展開）を基本
    - セキュリティソフトでの誤検知: 可能性があることを注記（PyInstaller使用による）
    - Pythonバージョン: 3.11.x（exe配布前提のためバージョン固定）
  - **受け入れ条件**: Windows 10/11（64bit）環境で、Python未インストールでも実行ファイルを起動できること

## 3. 非機能要件

### 3.1 パフォーマンス
- **NFR-001**: 大量のファイルをダウンロードする場合でも安定して動作すること
  - **受け入れ条件**: 100件以上のファイルをダウンロードしてもメモリリークなく動作すること
- **NFR-002**: ダウンロード処理の並列化を検討すること（オプション）
  - **受け入れ条件**: 設定で並列数を指定し、複数ファイルを同時ダウンロードできること（将来拡張）
- **NFR-002-1**: 定期実行と通知を非常駐で実行すること
  - **受け入れ条件**: 常駐トレイ、常駐通知監視、Windowsサービスを使わず、GUI、ジョブ、通知が終了した後にippi-down由来のプロセスが残らないこと

### 3.2 セキュリティ
- **NFR-003**: ユーザー認証情報を平文で保存しないこと
  - **受け入れ条件**: 設定ファイルに認証情報を平文で保存しないこと
- **NFR-004**: 外向き通信は通信セキュリティ正本の固定許可リストへ限定すること
  - **受け入れ条件**: HTTPS、host、path、Method、query形式、用途および各redirect hopを送信前に検証し、未知の通信を既定拒否すること
  - **受け入れ条件**: proxy、TLS検証無効化、client certificate、HTTP認証、任意Host headerを許可しないこと
  - **受け入れ条件**: 標準テストは実socketとDNSを遮断し、許可／拒否を保存済みfixtureで検証すること
  - **正本**: [外向き通信・ローカル実行セキュリティ仕様](network_security.md)

### 3.3 エラーハンドリング
- **NFR-005**: ネットワークエラー、ファイルシステムエラーなどに対して適切にエラーハンドリングを行うこと
  - **HTTPタイムアウト設定**:
    - 接続タイムアウト: 10秒（設定可能）
    - 読み込みタイムアウト: 60秒（設定可能）
    - **適用範囲**: すべてのHTTPリクエスト（ページ取得、ファイルダウンロード、POSTリクエスト等）に適用
    - 注: 回線が遅い環境でも無限待ちを避けるため、タイムアウト値は必須
  - **受け入れ条件**: ネットワークエラー、ファイルシステムエラー発生時に適切なエラーメッセージを表示し、処理を継続できること。タイムアウト時は適切にエラーとして記録すること
- **NFR-006**: エラー発生時も処理を継続できること（可能な限り）
  - **受け入れ条件**: 1件のファイルダウンロードに失敗しても、他のファイルのダウンロードを継続できること

### 3.4 保守性
- **NFR-007**: コードに適切なコメントを記述すること
  - **受け入れ条件**: 主要な関数・クラスにdocstringを記述すること
- **NFR-008**: 設定ファイルの形式を明確にドキュメント化すること
  - **受け入れ条件**: 設定ファイルの各項目について、READMEまたは設定ファイル例に説明を記載すること

## 5. データ要件

### 5.1 設定データ（YAML形式）

設定ファイルのスキーマを以下に示す。各項目の型と説明は実装設計書を参照。

```yaml
# 対象URL（検索画面）
target:
  url: string  # 検索画面URL（例: https://www.i-ppi.jp/.../Search.aspx?tab=4）

# フィルタ条件
filters:
  file_types: array[string]  # 拡張子リスト（例: [".pdf", ".xlsx"]）
  keywords: array[string] | string  # キーワード（配列または文字列）
  date_range:
    start: string | null  # YYYY-MM-DD形式
    end: string | null

# ダウンロードデータルートと保存構成
save_paths:
  local: string  # 通常実行と定期実行をまとめるデータルート
  layout_version: integer  # 新規設定は4、明示済みv3は維持、キーがない旧設定は2
  normal_folder: string  # 既定: 01_通常ダウンロード
  scheduled_folder: string  # 既定: 02_定期実行
  schedule_storage_key: string  # S001形式。定期設定の登録・複製時に発行
  schedule_storage_folder: string  # 固定キーと設定の初回名称から生成

# ファイル命名規則
naming_rule: string  # 既定: "{document_name}_{document_updated_at}"

# ダウンロード設定
download:
  retry:
    count: integer  # リトライ回数（デフォルト: 3）
    backoff: boolean  # 指数バックオフ使用（デフォルト: true）
  timeout:
    connect: integer  # 接続タイムアウト（秒、デフォルト: 10）
    read: integer  # 読み込みタイムアウト（秒、デフォルト: 60）

# 旧単一定期実行との互換設定
schedule:
  enabled: boolean
  backend: "windows_task_scheduler"
  timezone: "Asia/Tokyo"
  interval: string  # daily, weekly, monthly
  time: string  # HH:MM形式
  weekday: string  # weekly時、monday～sunday
  day_of_month: integer  # monthly時、1～28
  start_when_available: boolean
  wake_to_run: boolean
  retry_count: integer  # 一時障害だけ再試行
  retry_interval_minutes: integer
  notification_policy: string  # off / important_only / all_results / failures_only
  active_profile_id: string | null  # 旧設定の読込互換用

# 名前付き定期実行はGUI管理台帳で複数保持する
schedule_definition:
  schedule_id: string        # 名称や条件を変更しても不変の内部ID
  display_name: string       # 1～80文字、空白を除く大文字小文字非依存で一意
  storage_key: string        # S001形式の不変保存キー
  storage_folder: string     # 表示名変更でも変えない保存フォルダ
  enabled: boolean
  snapshot_id: string        # 現在登録中の不変条件版ID
  task_name: string
  created_at: datetime
  updated_at: datetime

# ログ設定
logging:
  level: string  # DEBUG, INFO, WARNING, ERROR（デフォルト: INFO）
  path: string  # ログファイルパス
  max_bytes: integer  # 最大ファイルサイズ（バイト、デフォルト: 10485760 = 10MB）
  backup_count: integer  # ローテーション世代数（デフォルト: 5）
```

定期実行の管理ファイルは配置単位です。`config/schedule-instance-id`はWindowsタスク名のtask namespace、`config/schedule-registration.json`と`config/schedule-profiles/`はその配置が管理する台帳と不変スナップショットです。`%LOCALAPPDATA%\ippi-down\install-id`は同じWindowsユーザー内の全配置で共有するcoordination IDで、FIFOと排他制御にだけ使用します。

**注**: 詳細なスキーマ定義とデフォルト値は実装設計書を参照すること。

### 5.2 ログデータ

#### 5.2.1 ログ出力フォーマット
- **通常ログ**: テキスト形式（人が読む形式）
  - フォーマット: `[YYYY-MM-DD HH:MM:SS] [LEVEL] [MODULE] - MESSAGE`
- **失敗ログ**: JSON Lines形式（1行1イベント、機械が読む形式）
  - 必須フィールド:
    - `url`: 対象URL
    - `status_code`: HTTPステータスコード（エラーの場合）
    - `error_type`: エラー種別（timeout, connection_error, http_error等）
    - `retry_count`: 再試行回数
    - `timestamp`: エラー発生時刻（ISO 8601形式）
    - `message`: エラーメッセージ

#### 5.2.2 ログデータの内容
- 実行日時
- ダウンロードしたファイル一覧
- エラー情報（上記JSON Lines形式）
- 実行結果サマリー（成功/失敗/スキップ件数、失敗理由別件数）

## 7. 制約事項

### 7.1 技術的制約
- i-ppi.jpのHTML構造が変更された場合、解析ロジックの修正が必要になる可能性がある
- ネットワーク接続が必要
- Windows 10/11（64bit）環境のみサポート

### 7.2 法的・倫理的制約
- i-ppi.jpの利用規約を遵守すること
- robots.txtを確認し、クローリングが許可されているか確認すること
- 過度なリクエストを送信しないこと（レート制限の考慮）
  - **レート制限の目安**: 1〜2 req/sec（429エラーが発生した場合は自動的に待機）
  - **User-Agent**: 対象サイトとの互換性を確認した固定値を一貫して使用する。通信先とHTTPヘッダーのルールは[**外向き通信・ローカル実行セキュリティ仕様**](network_security.md)を正本とする
  - **社内利用形態**: 社内端末での利用形態（ログイン有無、規約の禁止条項）を確認すること
- **対応範囲の明確化**: 本ツールはログインを必要としない範囲を対象とする
  - ログインが必要な機能や、認証が必要なファイルへのアクセスは対象外
  - ログイン機能が必要になった場合は、認証方式（ID/PW/OAuth/CAPTCHA等）を別途検討する

## 9. 受け入れ試験（Acceptance Test）

本ツールの承認時に実施する受け入れ試験項目を以下に示す。

### 9.1 基本機能の受け入れ試験

- **AT-01: 条件指定によるファイル取得**
  - **試験内容**: 
    1. GUI上で検索条件を設定（ファイルタイプ、キーワード、日付範囲等）
    2. ダウンロードを実行
    3. 取得可能な添付ファイルが保存先に保存されることを確認
    4. 実行結果サマリーの件数が実際の保存件数と一致することを確認
  - **合格基準**: 
    - 設定した条件に一致するファイルが正しく保存されること
    - サマリーの成功件数が保存ファイル数と一致すること
    - 失敗したファイルはログに記録され、サマリーに反映されること

- **AT-02: 429エラー時の待機動作**
  - **試験内容**: 
    1. 429エラーが発生する状況を模擬（模擬方法は以下いずれか）
       - テスト用に意図的に高頻度アクセス（ただし規約に抵触しない範囲）
       - ローカルの簡易HTTPサーバーで 429 を返すモックを用意
       - requests のアダプタ/モック（responses等）で 429 + Retry-After を再現
    2. `Retry-After`ヘッダーが存在する場合はその値に従って待機することを確認
    3. `Retry-After`ヘッダーが存在しない場合は指数バックオフで待機することを確認（最大60秒）
    4. 待機後にリトライが実行されることを確認
  - **合格基準**: 
    - 429エラー時に適切な待機時間を確保すること
    - `Retry-After`ヘッダーを優先的に使用すること
    - 待機後にリトライが実行され、成功する場合はファイルが保存されること

- **AT-03: 実行中のキャンセル処理**
  - **試験内容**: 
    1. ダウンロード処理を開始
    2. 処理中にキャンセルボタンをクリック
    3. 進行中の通信が中断されることを確認
    4. 処理中の`.part`ファイルだけが削除されることを確認
    5. GUIが固まらず、正常に終了することを確認
  - **合格基準**: 
    - キャンセル操作後、通信が即座に中断されること
    - `.part`ファイルが削除され、既存の正常ファイルが保持されること
    - GUIが応答し続け、エラーなく終了すること
    - ログにキャンセル情報が記録されること

- **AT-04: 配置別の定期実行管理と明示移行**
  - **試験内容**:
    1. 同じWindowsユーザーで2つの配置から定期実行を登録する
    2. 各配置の通常一覧に自配置の設定だけが表示され、別配置は管理外件数と専用一覧に表示されることを確認する
    3. 旧`config`フォルダーを選択し、previewから検証済みの1件を取り込む
    4. 検証不能な孤立タスクについて確認付き解除を行う
  - **合格基準**:
    - 配置ごとのtask namespace IDが異なり、coordination IDだけを共有すること
    - 移行中は新旧タスクが同時に有効にならず、最終的に移行元の有効／無効状態を現在のexe用の設定へ引き継ぐこと
    - 移行元が`MIGRATED_OUT`となり、旧タスクが無効化後に削除されること
    - 実行中の外部タスクは解除できず、旧`config`、取得文書、元の履歴を削除しないこと

- **AT-05: 実行中・順番待ちの定期実行編集と小画面での操作**
  - **試験内容**:
    1. 登録済みの管理対象を実行中、順番待ち、再試行待機中として表示する
    2. 各状態で複製・編集・削除・有効化／無効化の操作可否と、今すぐ実行の操作可否を確認する
    3. 編集確認後に条件を保存し、既存の実行と次回の登録条件を確認する
    4. 狭い作業領域で設定画面を開き、ボタンとフッター、登録内容、履歴の右端の列まで確認する
  - **合格基準**: 管理操作が使え、今すぐ実行は重複起動しない。既存の実行は登録時のスナップショットで継続し、次回以降は新条件となる。必要な操作と情報へスクロールで到達できる
